Haas on Apple Silicon

019 · Use vDSP for the frontend

rejected

The vDSP FFT shortened the host frontend by 9.31% to 17.89% on three public clips. Median paired whole-request reductions on nine inputs were -0.366% for Q4_K, -0.286% for Q8_0 and +0.236% for F16. Each format changed direction across the three rounds, so the trial stopped at the screen.

Machine-readable report JSON · Tracking issue

Measured scope: 9 inputs × 3 latency rounds per side; 9 quality inputs per side. CPU decoding with 4 threads.

Four CPU threads are an explicit tuned campaign setting, not the runtime default. Unspecified threads (threads=0) use performance cores: 16 on this M2 Ultra. Code gains compare the tuned anchor and do not include the preliminary thread-tuning gain; measure 021 evaluates automatic versus four threads separately.

Conditions and limitations

Time from before sending the first PCM16 chunk through receipt of the terminal result. File reading, model loading and warmup are excluded. Each measured input is warmed once per fresh worker.

Median over rounds for each input, then linearly interpolated p50, p90 and p99 across the measured input medians. RTFx divides total audio duration by summed request time.

Literal CER: Total Unicode code-point Levenshtein edits divided by total reference code points, including punctuation, symbols and whitespace.

Repository CER: NFKC followed by removing Unicode punctuation, symbols, separators and whitespace; no case folding or alternate-spelling substitutions. Edits and reference lengths are summed before division.

  • The current corpus is FLEURS Japanese test, with inputs from 6.36 to 28.2 seconds.
  • The p99 of a small duration-stratified sample is not a precise estimate of production tail latency.
  • The repository CER is not the published metric accepting alternative spellings of words.
  • Fresh-process load and first-request times do not reset filesystem or system Metal caches.
  • The full 30-input latency and 650-input accuracy evaluation and the six 2/4-second prefixes were not run. Percentiles and CER in this report use the nine-input screen only. Each duration stratum has three inputs.
  • Official reference comparisons cover the frontend of the pinned encoder path. Full official KDA/TDT, raw decoder IDs, frame indices and durations remain unverified. Real non-Haas and Sortformer runtime, Windows/Vulkan, non-Apple refusal and allocation-fault injection were untested.
  • The screen used a Metal encoder and greedy CPU4 decoder on one Mac. Voimem default decoder placement and automatic thread settings were untested. Gross process peak memory includes every worker allocation, including the opaque Accelerate setup.
  • The matched original and candidate used native arm64 Release with explicit SDK and architecture. After normalizing build paths, 73 of 74 common compiler flag files and 15 of 74 common link files matched literally. The entire token comparison accounted for one SDK framework search path, a change in Accelerate link order in 57 files, the frontend factory object in one archive and the vDSP object in a second archive. The remaining architecture, SDK and optimization flags matched.
  • The primary comparison uses one measured binary with explicit selector OFF or ON. The historical fixed anchor selected architecture and SDK implicitly. Their effective equivalence to the explicit options in the matched native build pair was unverified. Source-114 controls retained from trial 018 supply public outputs only. Their elapsed times are excluded.
  • First request is the first warmup request on a fresh worker. Ready and first-request figures are separate from warm request latency.
