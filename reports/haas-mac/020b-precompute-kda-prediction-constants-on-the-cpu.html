Haas on Apple Silicon

020b · Precompute KDA prediction constants on the CPU

rejected

CPU-only KDA constant preparation shortened paired warm requests by 1.076% on Q4_K and 0.257% on F16. Q8_0 slowed by 0.589%. Each format changed direction across the three rounds and all three were slower than the separate fixed anchor.

Machine-readable report JSON · Tracking issue

Measured scope: 9 inputs × 3 latency rounds per side; 9 quality inputs per side. CPU decoding with 4 threads.

Four CPU threads are an explicit tuned campaign setting, not the runtime default. Unspecified threads (threads=0) use performance cores: 16 on this M2 Ultra. Code gains compare the tuned anchor and do not include the preliminary thread-tuning gain; measure 021 evaluates automatic versus four threads separately.

Conditions and limitations

Time from before sending the first PCM16 chunk through receipt of the terminal result. File reading, model loading and warmup are excluded. Each measured input is warmed once per fresh worker.

Median over rounds for each input, then linearly interpolated p50, p90 and p99 across the measured input medians. RTFx divides total audio duration by summed request time.

Literal CER: Total Unicode code-point Levenshtein edits divided by total reference code points, including punctuation, symbols and whitespace.

Repository CER: NFKC followed by removing Unicode punctuation, symbols, separators and whitespace; no case folding or alternate-spelling substitutions. Edits and reference lengths are summed before division.

  • The current corpus is FLEURS Japanese test, with inputs from 6.36 to 28.2 seconds.
  • The p99 of a small duration-stratified sample is not a precise estimate of production tail latency.
  • The repository CER is not the published metric accepting alternative spellings of words.
  • Fresh-process load and first-request times do not reset filesystem or system Metal caches.
  • The original 114c514 and the 020b candidate matched on 74 compiler and 74 linker recipes after source/build directory normalization. Both actually used explicit arm64 and SDK flags. The fixed performance anchor used implicit architecture/SDK selection. Its effective defaults were not proven identical.
  • All whole-request screen values use explicit four-thread CPU decoding and a Metal encoder. The first-request metric is the first warmup request in each fresh process. The peak is the maximum whole-process footprint of three timed workers and their quality worker.
  • Full-corpus timing, full-corpus recognition accuracy and a separate short-only repeat were not run. The measured quality comparison covers the nine public screen files. Keyword contract/output gates used three recordings; keyword-boost latency and live ASR latency were not measured.
  • The ordinary worker does not expose raw TDT IDs, frame indices, duration decisions or individual KDA tensors. Its published token/segment arrays are checked separately from the dedicated C++ comparison. Official KDA, recurrent-state and complete TDT references were unavailable. The available official encoder reference does not independently validate the changed prediction stage.
  • The M2 Ultra mixed Metal-encoder/CPU4 workload is the measured primary configuration. Other Macs, Windows Vulkan and end-to-end GPU-decoder performance were not evaluated. The selector stays off by default.
