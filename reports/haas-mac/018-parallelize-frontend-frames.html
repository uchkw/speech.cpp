Haas on Apple Silicon

018 · Parallelize frontend frames

conditional

F16 with a Metal encoder and a four-thread CPU decoder reduced median paired latency by 2.799%, with all 30 full-run inputs faster. Q4_K and Q8_0 each slowed in one duration stratum. The full public outputs matched at every format. Parallel frontend frames remain a candidate for F16 on longer inputs with this placement.

Machine-readable report JSON · Tracking issue

Measured scope: 30 inputs × 3 latency rounds per side; 650 quality inputs per side. CPU decoding with 4 threads.

Four CPU threads are an explicit tuned campaign setting, not the runtime default. Unspecified threads (threads=0) use performance cores: 16 on this M2 Ultra. Code gains compare the tuned anchor and do not include the preliminary thread-tuning gain; measure 021 evaluates automatic versus four threads separately.

Conditions and limitations

Time from before sending the first PCM16 chunk through receipt of the terminal result. File reading, model loading and warmup are excluded. Each measured input is warmed once per fresh worker.

Median over rounds for each input, then linearly interpolated p50, p90 and p99 across the measured input medians. RTFx divides total audio duration by summed request time.

Literal CER: Total Unicode code-point Levenshtein edits divided by total reference code points, including punctuation, symbols and whitespace.

Repository CER: NFKC followed by removing Unicode punctuation, symbols, separators and whitespace; no case folding or alternate-spelling substitutions. Edits and reference lengths are summed before division.

  • The current corpus is FLEURS Japanese test, with inputs from 6.36 to 28.2 seconds.
  • The p99 of a small duration-stratified sample is not a precise estimate of production tail latency.
  • The repository CER is not the published metric accepting alternative spellings of words.
  • Fresh-process load and first-request times do not reset filesystem or system Metal caches.
  • The full tests cover public FLEURS inputs from 6.36 to 28.2 seconds. The 30 input medians provide a limited estimate of production tail latency. Three source recordings cannot establish accuracy or typical timing for naturally completed short utterances.
  • No official full KDA/TDT, Windows/Vulkan, real non-KDA/Sortformer, injected task-creation or allocation-failure test was run. The worker does not expose raw TDT IDs, frame indices or durations.
  • Evidence for this F16 candidate covers a Metal encoder and CPU4 decoder. Default Voimem decoder placement and automatic thread counts require their own evaluation. Peak process footprint includes all worker allocations. The host FFT span does not provide a breakdown of kernel or device memory.
  • The fixed timing anchor used implicit architecture and SDK defaults. Effective equivalence to the matched original and candidate builds, which set arm64 and the SDK explicitly, was unverified. The primary OFF/ON comparison uses one executable.
  • Load to ready and the first request are separate startup observations. The first-request column is the median time for the first warmup input in each fresh latency worker. The warm request percentiles use the later measured inputs.
